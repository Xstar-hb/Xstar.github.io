OWASP Top 10 漏洞详解

2021版 · 深度解析与防御指南

前言

OWASP（Open Web Application Security Project）发布的 Top 10 是全球 Web 安全领域最具影响力的漏洞风险清单之一。

它不是“10个漏洞名字”的简单罗列，而是：

  • Web 应用最常见的攻击面总结
  • 企业安全建设的最低基线
  • 渗透测试、代码审计、SDL、安全开发的重要参考
  • 面试、安全岗、CTF、攻防演练高频知识点

很多人学习漏洞时有个致命问题：只会“打漏洞”，不会理解漏洞为什么会存在。

真正重要的是理解：

  • 漏洞形成条件
  • 系统设计缺陷
  • 攻击链组合方式
  • 防御边界
  • 开发中的错误思维

A01 Broken Access Control（访问控制失效）

漏洞本质

系统没有正确限制“谁能访问什么”。这是目前最危险、最常见的漏洞类型之一。

本质问题：系统默认相信用户。 攻击者不需要破解密码，只需要修改 ID、越权访问接口、猜测资源路径或伪造请求，即可访问不属于自己的数据。

常见类型

1. 水平越权
用户A访问用户B的数据。例如：/user/info?id=1001 修改为 /user/info?id=1002，如果返回别人数据，就是水平越权。

2. 垂直越权
普通用户获取管理员权限。例如：调用 /admin/deleteUser，后台未验证管理员身份。

3. 接口未鉴权
前端隐藏了按钮，但后端接口仍可直接调用。很多开发误以为：“前端看不见 = 安全”。这是典型错误，安全必须由服务端控制。

防御方案

  • 必须遵循：默认拒绝。系统默认不允许访问，而不是“默认允许，再做限制”。
  • 服务端统一鉴权。不要依赖前端按钮隐藏、JS 判断或页面跳转限制。所有接口都必须校验身份、权限和资源归属。
  • RBAC 权限模型。推荐：用户 -> 角色 -> 权限。而不是直接给用户权限。

A02 Cryptographic Failures（加密机制失效）

漏洞本质

不是“没加密”，而是：“错误地使用了加密”。

很多开发会使用弱算法、明文存储密码、自己设计加密、使用固定 IV 或传输不走 HTTPS。这会导致数据即使“看起来加密了”，也能被恢复。

常见问题

1. 明文存储密码

password = 123456

数据库一旦泄露，全站沦陷。

2. 使用 MD5/SHA1
很多人仍然认为 MD5 = 安全。这是严重错误，MD5 已被彩虹表、GPU 暴力破解。

3. 自己设计加密算法
安全领域有个经典结论：不要自己发明密码学。因为 99% 的自定义加密都存在致命缺陷。

正确方案

  • 密码存储：使用 bcrypt、scrypt、Argon2。
  • 全站 HTTPS：不仅登录页，所有页面都必须 HTTPS。
  • 密钥隔离：不要把 key、数据库密码、JWT 密钥写进代码仓库。

A03 Injection（注入漏洞）

漏洞本质

用户输入被当成代码执行。这是 Web 安全最经典的漏洞类型。核心原因：数据和代码没有分离。

常见注入类型

  • SQL 注入：SQL 被拼接执行
  • XSS：JS 被浏览器执行
  • 命令注入：系统命令被执行
  • LDAP 注入：LDAP 查询被污染

经典示例

SQL 注入错误代码：

SELECT * FROM users WHERE username='admin' AND password='123456'

攻击者输入：' OR 1=1 -- 可能直接绕过登录。

命令注入错误示例：ping + user_input。攻击者输入：127.0.0.1 && rm -rf /，后果极其严重。

防御方案

  • 永远不要字符串拼接 SQL。必须使用 PreparedStatement、参数化查询或 ORM。
  • 输出编码。针对 HTML、JS、URL 分别转义。
  • 输入白名单。不是过滤危险字符，而是只允许合法输入。这两者差别巨大。

A04 Insecure Design（不安全设计）

漏洞本质

不是代码写错，而是系统从设计阶段就存在安全缺陷。很多团队把安全当“补丁”。真正成熟的团队：在架构阶段就考虑攻击路径。

典型问题

  • 没有限流：导致暴力破解、短信轰炸、验证码爆破。
  • 密码找回逻辑弱：例如只验证手机号后4位。
  • 多租户隔离失败：一个客户读取另一个客户数据。

核心思想与推荐方法

安全不是“上线前修几个洞”，而是系统设计阶段就进行威胁建模。

微软经典 STRIDE 威胁建模方法：

类型含义
S (Spoofing)身份伪造
T (Tampering)数据篡改
R (Repudiation)抗抵赖失败
I (Information Disclosure)信息泄露
D (Denial of Service)拒绝服务
E (Elevation of Privilege)权限提升

A05 Security Misconfiguration（安全配置错误）

漏洞本质

系统默认配置不安全。这是企业里极其高频的问题。因为很多系统上线时：“先跑起来再说”。

常见错误

  • 默认密码：例如 admin/admin, root/123456。
  • 开启目录浏览：攻击者直接下载配置文件、备份文件、日志。
  • Debug 模式开启：错误信息暴露 SQL、文件路径、堆栈、Token。

防御方案

  • 删除默认账号
  • 关闭调试模式
  • 最小权限原则
  • 配置审计与自动化基线检查

A06 Vulnerable and Outdated Components（存在漏洞的组件）

漏洞本质

你自己的代码可能没漏洞，但你依赖的组件有漏洞。现代系统大量依赖开源框架、第三方 SDK、Docker 镜像等。供应链攻击越来越危险。

典型案例

  • Log4Shell：Java 安全史上最著名漏洞之一。攻击者通过日志即可远程执行代码，影响全球。
  • Fastjson AutoType：Java 常见高危反序列化漏洞。

防御方案

  • 建立 SBOM (Software Bill of Materials)：知道系统用了哪些组件。
  • 自动化漏洞扫描：例如 Dependabot, Snyk, Trivy。
  • 及时升级：不要“等出事再升级”。

A07 Identification and Authentication Failures（身份认证失效）

漏洞本质

系统无法正确确认：“你到底是谁”。

常见问题

  • 弱密码：例如 123456, admin。
  • Session 固定：攻击者提前设置 SessionID，用户登录后被接管。
  • Token 永不过期：JWT 长期有效，泄露后永久可用。

防御方案

  • 强密码策略：限制长度、复杂度，使用黑名单密码。
  • MFA 多因素认证：推荐 TOTP、FIDO2、硬件密钥。
  • 登录限速：防止暴力破解。

A08 Software and Data Integrity Failures（完整性失效）

漏洞本质

系统默认相信更新包、插件、CI/CD、第三方代码，但没有验证完整性。

常见问题

  • 不安全反序列化：攻击者构造恶意对象，导致远程代码执行。
  • CI/CD 被攻击：攻击者污染构建流程，发布恶意代码。

防御方案

  • 软件签名与校验 Hash
  • Zero Trust CI/CD
  • 禁止反序列化不可信数据

A09 Logging and Monitoring Failures（日志与监控失效）

漏洞本质

系统被攻击了，但你不知道。很多企业不是“没被攻击”，而是根本没发现。

常见问题

  • 不记录关键日志：例如登录失败、权限变更、数据导出。
  • 无告警系统：即使日志异常也没人知道。

防御方案

  • 建立 SIEM：例如 Splunk, ELK, Wazuh。
  • 建立攻击告警规则：例如短时间大量登录失败、异地登录告警。

A10 SSRF（服务端请求伪造）

漏洞本质

攻击者让服务器替自己发请求。因为服务器通常权限更高，能访问内网或云元数据。攻击目标不是 Web 本身，而是内网。

常见场景

云环境高危：攻击者访问 169.254.169.254 获取云主机元数据。可能直接获取 AK/SK、IAM Token、临时凭证。

防御方案

  • URL 白名单：不要允许任意 URL。
  • 禁止访问内网地址：过滤 127.0.0.1、localhost 及内网 IP。
  • 网络隔离：业务服务器不要直接访问核心内网。

真正危险的不是“漏洞”

很多新人学安全只盯着漏洞名字，这是远远不够的。真正危险的是：系统性安全失败。

  • 权限模型错误
  • 安全边界不存在
  • DevOps 缺少安全
  • 开发默认信任用户输入

漏洞只是结果，设计缺陷才是根源。

企业安全建设建议

  • 第一阶段：建立最低安全基线。做到 HTTPS、MFA、权限控制、参数化查询、日志监控。
  • 第二阶段：安全左移。在开发阶段引入 SAST、DAST、威胁建模。
  • 第三阶段：零信任。默认不信任用户、网络、内部系统、第三方组件。

学习建议

不要只停留在背漏洞名字、用扫描器。你应该深入理解操作系统、网络协议、Web 架构、数据库、编译原理、权限模型。

因为：安全本质上是“系统理解能力”，不是工具熟练度。
